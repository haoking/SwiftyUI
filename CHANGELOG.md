# Changelog

## 2.1.0

A cancellation release for `SwiftyPromise`. Before this version, `Sources/SwiftyPromise.swift` never once looked at `isCancelled`, so a chain had no idea the operations backing it had been cancelled — while `SwiftyThreadPool` cancels every operation in its queue the moment the app takes a memory warning. Cancellation now produces an error the caller can see, instead of a silently wrong result or a permanent hang.

Scope: GitHub issues [#3](https://github.com/haoking/SwiftyUI/issues/3), [#4](https://github.com/haoking/SwiftyUI/issues/4) and [#5](https://github.com/haoking/SwiftyUI/issues/5), plus two `value()` defects that no issue recorded — the hang path in the second entry under **Fixed**, which is the most serious defect in this release, and the discarded-error paths in the third.

There are no breaking changes. Every existing signature is unchanged; the behaviour changes are confined to paths that previously had no contract worth depending on.

### Added

- `PromiseError` — the errors the promise machinery produces itself, as distinct from the errors your own task bodies throw. It is `public enum PromiseError: Error, Sendable, Equatable`, with two cases:
  - `.cancelled` — the operation backing a task was cancelled before its block started running. The usual source is `SwiftyThreadPool.removeAll()`, which the shared pool calls for you when a memory warning arrives.
  - `.noValue` — the chain settled without any task ever having called `update(...)`, so there is no value to hand back. `Promise.value()` never throws this: it returns `nil` in that situation, as it always has. The only producer in the library is `UIImage.colors()`, where a missing value can only mean the image was deallocated before the analysis began.
- `UIImage.colors() async throws -> (background: UIColor, primary: UIColor, secondary: UIColor, detail: UIColor)` — an `async` variant of the existing callback-based `colors(_:)`. Same analysis, same four colours, in the same order. Two things differ: failure and cancellation are thrown rather than swallowed, and the result arrives on whatever context you awaited from — the callback version hops to the main queue first, this one has no such hop and needs none. The callback version's signature and behaviour are untouched — see the `colors(_:)` entry under **Changed** for why you might want the new one.

### Fixed

- **A cancelled task now fails its chain with `PromiseError.cancelled`.** (issue #3) A cancelled operation does not run its block, but it _does_ run its completion block — and the completion block is exactly where `fire()` attaches its "advance to the next step" logic. So the chain advanced as though nothing had happened: it skipped the cancelled step, carried on with whatever value the _previous_ step had left in place, ran every remaining step against that stale value, and settled **successfully**. Nothing in the caller-visible outcome distinguished this from a chain that ran in full. Cancellation is now detected in that same completion block and routed through the existing error path: the remaining tasks are discarded, `always` tasks still run, and your `catch(_:)` handler — or an outstanding `value()` — receives `.cancelled`.
  Note that `start()` still gives the error nowhere to go: it registers no handler by design, so a cancelled chain terminated with `start()` simply stops. Terminate with `catch(_:)` or `value()` if you need to hear about it. The same is true of an `always` task of your own that gets cancelled: it is silently skipped, because by the time `always` tasks run the chain has already settled and there is no error path left to put anything into.
- **`try await promise.value()` no longer hangs forever when the chain is cancelled.** This one is not in issue #3 — it was found while implementing the fix above, and it was introduced by 2.0's own `async` bridge, so it has only ever existed in 2.0.0. `value()` is built on top of `always`: it appends an `always` task whose entire job is to resume the continuation. In 2.0, `fire()` dispatched `always` tasks with **no completion block at all**, so a cancelled one simply never ran and never resumed anything. The `await` was left suspended with no timeout, and it does not respond to Swift `Task` cancellation either (it never has — that is documented). A single memory warning was enough to reach it, since the shared pool cancels its whole queue when one arrives. `always` tasks now carry the same cancellation-aware completion block as chain tasks, and the one `value()` installs resumes the continuation with **the chain's final value**. It deliberately does not throw `.cancelled` there. `always` tasks are dispatched once the chain has settled — by erroring as much as by succeeding — but every error path calls `markError`, and so resumes the continuation, strictly _before_ that dispatch. So if the chain errored, the `await` has already been given the error and this cancellation can no longer change the outcome; and if it has not been resumed by then, the chain succeeded and the result is computed and correct. Throwing `.cancelled` would discard a finished result to report a cancellation of nothing but the library's own bookkeeping, which is exactly the mistake the `isCancelled && !didRun` rule under **Changed** exists to prevent. (2.0 suspended permanently in this situation, so there is no behaviour anyone can have depended on.)
  **This does not make `value()` hang-proof, and it should not be read as "cancellation is solved".** Cancelling an operation does not by itself end it — the queue ending it is what triggers the completion block — so the fix holds only while the queue can still drain. There are three **known** cases in which it still will not return, and `value()`'s documentation comment lists them too:
  1. the pool was `stop()`ped and never `restart()`ed, so the queue is not running at all;
  2. the pool was `cancel()`ed at any point before the chain's next background task was dispatched — `cancel()` drops the internal queue, and `add` silently discards everything after that, so that task never enters a queue and never gets a completion block. This is not limited to a chain that was already doomed when it started: a `cancel()` landing mid-chain strands whatever step comes next;
  3. the pool was `removeAll()`ed or `cancel()`ed **while suspended** — a suspended queue finishes nothing, cancelled operations included, so no completion block fires. A `removeAll()` in this state is at least recoverable: `restart()` resumes the queue, it finishes the cancelled operations, and the completion blocks fire. `cancel()` is not. It sets the internal queue to `nil`, and `restart()` is `currentQueue?.isSuspended = false` — a no-op on `nil`. Nothing can bring that queue back, and every `await` waiting on it stays suspended for the life of the process.
     Case 3 is reachable in ordinary use — an app that calls `SwiftyThreadPool.default.stop()` when it goes to the background and then takes a memory warning hangs every in-flight `await`. Making `cancel()` / `stop()` drain the queue, or giving `value()` a deadline, is a behaviour change beyond this release's scope. It is stated here rather than fixed, and is tracked as [#6](https://github.com/haoking/SwiftyUI/issues/6).
- **`try await promise.value()` no longer discards an error the chain has already raised.** Two separate paths lost one. `value()` registers two things when it is called: an `always` task that will resume the continuation, and an internal error handler that will resume it by throwing. Those were **two independent critical sections**, so a chain that errored in between them found `internalErrorHandler` still `nil` — the error reached nobody, and `fire()` then ran the `always` task and resumed the `await` with whatever value the chain was holding. The caller got a plausible-looking result from a chain that had failed. The window is narrow, but it widens under contention on the state queue, and reaching it needs nothing exotic: any second terminator that has already put the chain in flight will do (`start()` then `value()`, `catch(_:)` then `value()`, two concurrent `value()` calls). The second path was simpler: calling `value()` on a chain that had **already settled with an error** returned the chain's last value, because the error object was never retained anywhere. Both are fixed by the same change — the terminated check, the errored check, the `always` append and the handler registration now happen inside a single critical section, and the error that terminated a chain is kept, so a late `value()` can rethrow it. This predates 2.1 (the ordering is unchanged since 2.0.0) and no issue recorded it, but it is a silently-wrong-result path inside the one method this release rewrote, which is the class of defect the release exists to remove.
- **Appending `then` or `always` to a chain that has already settled now trips an assertion in debug builds.** (issue #4) A `Promise` is single-use: once `start()`, `catch(_:)` or `value()` has terminated it and the chain has finished, `fire()` never drains those queues again, so anything appended afterwards can never run. In 2.0 that was completely silent — no error, no return value, no log; the task just went into a queue nobody would ever look at again. The "has it settled?" check and the append now happen inside a single critical section (so a chain settling concurrently cannot be slipped past), and a rejected append calls `assertionFailure`. Release builds keep 2.0's no-op behaviour, and both methods still return `self`, so chaining syntax is unaffected.
  Rejected appends were deliberately **not** made to execute immediately instead. That would stop `isFinished` being a terminal state, which the whole design uses as a one-way latch, and an immediately executed `then` that threw would have no one left to receive the error — trading one silent drop for another.

### Changed

- **Cancellation is detected as `isCancelled && !didRun`, not `isCancelled` alone.** `BlockOperation`'s block does not check for cancellation, so a cancel that lands _while_ a task is executing does not stop it — that work runs to completion. Treating it as cancelled would throw away a perfectly good result. So the rule is: **cancel means the chain fails, unless the work had already finished, in which case the chain carries on with it.** Each task carries a small lock-guarded flag its block sets on entry; Foundation runs the completion block after the operation ends, so the flag read there always reflects whether the block ran.
- **`UIImage.colors(_:)` — the callback version — does not call your callback if the analysis fails or is cancelled.** This has been true since 2.0, and it was written down nowhere — the user-visible failure is a spinner that never stops. The mechanism has changed underneath, though the outcome has not: in 2.0 a cancelled chain raised no error at all, and the callback was skipped because the step that would have invoked it found no value to pass on; from 2.1 cancellation _is_ an error, and the bare `.catch()` this method ends in discards it. It is now documented on the method, and `colors() async throws` exists for callers who need failure and cancellation reported rather than swallowed. Be precise about what that buys, though: the `async` variant is `Promise.value()` plus a nil check, so it **inherits all three of `value()`'s hang cases** listed above, case 3 included. It converts silence into a thrown error; it does not guarantee the `await` returns. A caller who switches to it and still needs a spinner to stop must impose its own deadline.
- **Compatibility.** Cancellation now produces an error where it previously produced a silently wrong result (a chain that "succeeded" on stale data) or an unrecoverable hang (`value()`). Neither of those was a contract anyone could reasonably have depended on, so nothing here is treated as breaking. What _can_ change for existing code: a `catch(_:)` handler that used to never fire on a memory warning may now fire with `PromiseError.cancelled`, and a chain that used to settle "successfully" with stale data now fails. Both are the point of the release. Debug builds will additionally trap on `then` / `always` appended after termination — code that was doing that was already dead code; check for it before shipping a debug build to testers.
- **Repository tooling** (issue #5). `Scripts/test.sh` and `Scripts/uitest.sh` used to take whatever the last available iPhone simulator happened to be, which makes the colour-extraction tests (sensitive to screen scale) and the geometry assertions (sensitive to window size) depend on what a given machine has installed. Both now pin a model — overridable with the `SWIFTYUI_SIMULATOR` environment variable, falling back to any available iPhone with a warning — and print the device they actually selected, so a failure that will not reproduce starts with a known machine. `Scripts/check-uitest-restore.sh` was updated to use the identical resolution logic: it verifies the simulator preference `uitest.sh` has to change is restored afterwards, and with a different rule it could have been checking a device `uitest.sh` never touched.

### Fixed

- **B1** Force-unwrap crash in `SwiftyGlobal.keyWindow` when there is no key window
- **B2** A static initializer constructed a `UINavigationController` (a UIKit object), which could run on a background thread on first access
- **B3** `ImageSettable`'s getter force-cast (`as! CGImage`) could crash, and the `CGImage` round trip lost `scale` and `imageOrientation`
- **B4** `ImageCachePool` used `sync` on a concurrent queue for write operations, causing data races with concurrent reads and the barrier-based writer
- **B5** Memory-usage accounting (`UInt64`) could underflow and trap
- **B6** The color-extraction sort predicate used `<=`, violating `sort(by:)`'s strict-weak-ordering requirement (undefined behavior)
- **B7** `SwiftyPromise`'s internal state was read and written across threads with no synchronization; concretely, `fire()` could hand the same `Operation` to `OperationQueue` twice, crashing the process with an uncaught `NSException`
- **B8** `SwiftyToastCenter`'s queue state was read and written across threads with no synchronization
- **B9** The thread pool's perpetual RunLoop operation was never actually enqueued, because `init` called `add` before assigning `self.queue`, and `add` reads the queue through `currentQueue` — still `nil`, so the operation was silently dropped. 2.0 fixes the assignment order **and then removes the operation altogether**, because once it genuinely ran it did far more harm than good:
  1. It made `SwiftyThreadPool` impossible to deallocate. The operation's closure strongly captures `self`, and its loop condition `while !Thread.current.isCancelled` never becomes true — `cancel()` sets the _operation_'s flag, not the thread's. The operation therefore never finished, the strong reference was never released, and `deinit` (including its B18 observer removal) was unreachable dead code.
  2. It permanently occupied one thread of a pool whose concurrency floor is 3.
  3. It did nothing. The `CFRunLoopSource` it created has a `nil` `perform` callback, so waking it executes nothing, and no code anywhere in the repository ever posted work to it.
  4. Removing it restores 1.x's observable behaviour exactly, since it never ran there either.
     The assignment-order constraint itself still stands and is documented in `init`: anything enqueued from `init` in the future must come after `self.queue = queue`. Regression test: `testPoolDeallocatesAfterCancel`, which also dropped that test case's runtime from 5.6 s to 0.5 s — the old 5 s was a poll waiting for a deallocation that could never happen
- **B10** `SwiftyThreadPool.stop()` / `restart()` had inverted semantics (`stop()` resumed the queue, `restart()` suspended it)
- **B11** The `always` handler ran before the rest of the chain instead of after it
- **B12** Integer division in the color-extraction threshold check made the `0.3` cutoff ineffective; fixed by switching to floating-point division. Fixing this also exposed a second, related problem in the same algorithm — see the dominant-color sort direction entry under Breaking Changes
- **B13** `isDistinct`'s inner near-gray check was dead code, unconditionally overwritten by the following line
- **B14** A per-call local `NSLock` in `UIImage.load` provided no real mutual exclusion — pure overhead, since a lock created fresh on every call never contends with anything. **This fix has no regression test of its own, permanently.** A lock that never contends with anything is behaviourally indistinguishable from no lock at all, so removing it changes nothing observable; `UIImage.load`'s thread safety came, and still comes, from the _shared_ lock inside `ImageCachePool` (B4). Mutation testing confirms the two are inseparable: putting the local lock back leaves `testConcurrentLoadIsSerializedByTheCachePoolLock` green, while removing `ImageCachePool`'s shared lock crashes it _whether or not_ the local lock is restored — which is precisely B14's point. That test is therefore a regression test for **B4**, not for B14; it is documented as such at its definition
- **B15** Implicit, process-wide swizzling of `backgroundColor`/`alpha` on every `UIView` in the host app, triggered lazily by the first call to `addTo(_:)`
- **B16** A `SwiftyPromise` chain with no `.catch()` never started and leaked (see the new `start()` API)
- **B17** `SwiftyGlobal`'s screen/status-bar metrics were cached once in static properties and went stale across rotation, split-screen, and multi-window
- **B18** `deinit` called `removeObserver(self)`, which is a no-op for observers registered via the block-based `addObserver(forName:object:queue:using:)` API — the token returned by that call is the real observer, not `self`. Fixed by storing and removing the token instead. **This fix is correctness-only and not user-visible in practice**: both affected types (`ImageCachePool.default`, `SwiftyThreadPool.default`) are singletons that live for the process's lifetime, so their `deinit` was never expected to run in production. `SwiftyThreadPool`'s `deinit` was, on top of that, unreachable altogether because of the perpetual RunLoop operation described under B9; now that the operation is gone, the fix can actually execute there too. `ImageCachePool`'s `deinit` does run for the short-lived instances created in tests
- **B19** `UIColor.hex(String)` force-unwrapped the result of `UInt(_:radix:)`, crashing on syntactically-valid-length but non-hexadecimal input (e.g. `hex("zzz")`)
- **B20** `SwiftyAlertView` registered **both** of its keyboard observers for `UIResponder.keyboardWillShowNotification`. The second observer's body is the keyboard-_hide_ logic (it checks `keyboardHasBeenShown` and restores the saved frame), so both ran on the same dispatch, in registration order: the first shifted the alert clear of the keyboard, the second immediately put it back and cleared the saved origin. Net displacement on every keyboard appearance: exactly zero. Meanwhile `keyboardWillHideNotification` was not observed at all. The second observer now registers for `keyboardWillHideNotification`.
  **This means keyboard avoidance in `SwiftyAlertView` has never worked in any released version**, and 2.0 is the first release in which an alert with `addTextField()` actually moves out of the keyboard's way. Regression tests: `testKeyboardAvoidanceFollowsShowHideLifecycle` (unit) and `testAlertWithTextFieldAvoidsKeyboard` (UI).
  Registration also moved off `viewDidAppear` / `viewDidDisappear` to `showTitle` / `hideView()`. This was **not** because the appearance callbacks fail to fire — measured on the iOS 26.5 simulator, they do fire, even though `showTitle` attaches the alert with a bare `addSubview` onto the key window, with no presentation, no view-controller containment, and no `rootViewController` relationship. Classic UIKit rules say a controller in that position should receive no appearance callbacks; the observed behaviour differs, and the library no longer depends on which is right. The new sites also buy two concrete things: registration pairs deterministically with the self-retain/release lifecycle this type already runs through `selfReference` (the no-key-window early return precedes registration, so the pairing invariant holds on every exit path), and `hideView()` unregisters _before_ the dismiss animation, so a late keyboard notification cannot shove an alert that is already on its way out.
- **B21** The keyboard observers were removed with `NotificationCenter.default.removeObserver(self, name:)`, which is a no-op for observers registered through the block-based `addObserver(forName:object:queue:using:)` API — the token that call returns is the observer, not `self`. Same root cause as B18, but on a type whose instances genuinely do deallocate: registrations would have accumulated two per alert shown, for the lifetime of the process, with every keyboard event firing all of them (and, combined with the `MainActor.assumeIsolated` in each block, a growing number of trap sites for any off-main keyboard post). Fixed by storing both tokens and removing them by token — the same shape now used at all three observer sites in the library. Re-registering also removes any previous pair first, so showing the same alert twice cannot strand a token. **Unlike B18, this leak was live in shipped builds**: the registration point did run, so every alert an app presented left two observers behind permanently.
  Unregistering also clears the keyboard bookkeeping (`tmpContentViewFrameOrigin`, `tmpCircleViewFrameOrigin`, `keyboardHasBeenShown`). Those three are written by the show-observer and cleared by the _hide_-observer — but `hideView()` unregisters **before** the dismiss animation, so dismissing an alert while the keyboard was still up left all three stale, the surviving half of the state waiting on a cleaner that no longer existed. Regression test: `testHidingWhileKeyboardIsUpLeavesNoStaleKeyboardState`
- **B22** `SwiftyToast` placed the toast entirely off-screen in landscape. `layoutView` swapped `containerSize`'s width and height before computing the position — correct for iOS 7 and earlier, where the window did not rotate with the interface and its `bounds` stayed portrait-sized, but wrong since iOS 8, where `window.bounds` already reflects the interface orientation. Swapping again rotated the result back into a portrait coordinate system. Measured on an iPhone 17 simulator (portrait window 402×874, landscape 874×402), the landscape toast landed at (132.5, 827) in a window only 402 points tall: nothing was visible at all. It now lands at (368.5, 355), centred against the bottom of the landscape window. Same defect class as B17 and the `UIScreen.main` removal — a static assumption about screen geometry that stopped holding many releases ago. Found by the UI tests added in this release; no prior test could reach it. Regression test: `testToastFollowsDeviceOrientation`.
  Fixing the swap alone was not enough, because the frame was still computed in `init` rather than at display time. `SwiftyToastCenter` is a serial queue and a toast takes ~3.5 s to play, so a toast created while another is showing waits before its `show()` runs — and a frame computed at construction is stale by then. That reproduced the same symptom through two other routes: rotating while a toast sits in the queue (it appears with the pre-rotation geometry, entirely off-screen in landscape), and constructing a toast before any key window exists (`containerSize` degenerates to `.zero`, giving a negative origin — measured at `(-109, -57, 218, 27)`). The layout now runs inside `show()`, after the `guard let window`, which fixes both and removes the `?? .zero` degenerate branch entirely. Regression test: `testGeometryIsNotComputedAtConstructionTime`.
  A toast **already on screen** now also follows rotation, via an `autoresizingMask` on the toast view: the width delta is split between two equal flexible side margins (so it stays horizontally centred) and the height delta is absorbed by a flexible top margin (so the bottom gap is preserved). Regression test: `testToastLabelReanchorsItselfWhenWindowResizes`

### Added

- `SwiftyGlobal.safeAreaInsets`
- `SwiftyThreadPool.isSuspended`
- `SwiftyPromise.start()` — a chain terminator that doesn't require an error handler
- `SwiftyPromise.value() async throws -> T?` — an `async`/`await` bridge. It registers its error handler in a slot of its own, separate from the one `catch(_:)` writes, so the two can be used together in either order: `catch(_:)` keeps its documented replace semantics for your handler without ever displacing an outstanding `await`, and `value()` never discards a handler you registered earlier. An error reaches your `catch` handler first, then resumes the `await` by rethrowing
- `SwiftyButton.ignoreEventInterval` — configurable double-tap debounce window (default `1.0`)
- `SwiftyUI.enableGlobalOpaqueOptimization()` — opt-in, process-wide, and irreversible; see Breaking Changes
- `ImageSettable.applyBackgroundImage(_:)` — pushes a `UIImage` onto `layer.contents` and updates `isOpaque`. It replaces the 1.x protocol extension's `backgroundImage` implementation, and **conformers must call it themselves** from their own `backgroundImage` `didSet`; see Breaking Changes and the README example
- `SwiftyToast.accessibilityIdentifier` — the identifier set on the toast view. `SwiftyLabel` draws its own text through TextKit rather than subclassing `UILabel`, so a toast was a silent coloured rectangle to VoiceOver and invisible to UI automation; it now exposes itself as a static-text accessibility element. The constant is declared `nonisolated`: `SwiftyToast` is `@MainActor`-isolated and its members inherit that isolation, which would have made this one unreferenceable from the nonisolated UI-automation code it exists to serve
