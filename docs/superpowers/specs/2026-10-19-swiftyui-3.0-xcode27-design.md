# SwiftyUI 3.0.0 设计:Xcode 27 升级与性能现代化

日期:2026-10-19
状态:待评审
目标版本:3.0.0(自 2.1.0 起的破坏性升级)

## 1. 背景

使用者已升级到 Xcode 27,要求"全面升级依赖和库",并"用最新、性能最高的方法"提升代码性能。

本仓库没有任何第三方依赖,所以"依赖"落在这几处:Swift 工具链门槛、最低 iOS 版本、示例工程的构建设置、CI 用到的 GitHub Action 与 runner、CocoaPods 发布链路。

### 1.1 实测现状

环境:Xcode 27.1(27A9275)/ Swift 6.4 / iOS 27.1 SDK,模拟器 iPhone 17(iOS 27.0)。

| 项目                                  | 结果                                                                                |
| ------------------------------------- | ----------------------------------------------------------------------------------- |
| 库构建(`Scripts/build.sh`)            | `BUILD SUCCEEDED`,0 告警                                                            |
| 单元测试(`Scripts/test.sh`)           | 156 个通过,1 个按设计跳过                                                           |
| `pod lib lint`(本机 CocoaPods 1.16.2) | 通过                                                                                |
| UI 测试(`Scripts/uitest.sh`)          | **6 个失败 5 个**:示例 App 一启动就崩溃                                             |
| 示例工程编译告警                      | UI 测试文件 121 条主 actor 隔离告警;5 条链接告警(部署目标 15.0 低于 XCTest 的 17.0) |

示例 App 的崩溃栈停在 `_UIApplicationEvaluateRuntimeIssueForNoSceneLifecycleAdoption`:**iOS 27 对用 iOS 27 SDK 构建、却没有采用 UIScene 生命周期的 App 直接 trap**。示例 App 还停在 2017 年模板的 AppDelegate + `window` 写法,Info.plist 里没有 `UIApplicationSceneManifest`。同一原因也让以示例 App 为宿主的 `iOSExampleTests` 跑不起来。CI 只构建示例工程、不运行它,所以一直是绿的。

UI 测试的 121 条告警来自 Xcode 27 的 XCUIAutomation:`XCUIApplication`、`XCUIElement`、`XCUIDevice` 等现在都标注了 `@MainActor`,而测试类是非隔离的。

### 1.2 Xcode 27 / Swift 6.4 带来的事实

- SDK 声明的部署目标:最低 iOS 15.0,**推荐 iOS 17.0**。
- `Synchronization` 模块的 `Mutex`、`Atomic`:iOS 18.0 起可用。`InlineArray`、`UTF8Span`:iOS 26.0 起可用。
- PackageDescription:6.2 新增 `.iOS(.v26)`、`treatAllWarnings`、`defaultIsolation` 等;6.4 新增 `.v27`。语言模式仍只到 `.v6`。
- Swift 6.4 的前瞻特性(Swift 7 默认开启):`ExistentialAny`、`InternalImportsByDefault`、`MemberImportVisibility`、`InferIsolatedConformances`、`NonisolatedNonsendingByDefault`、`ImmutableWeakCaptures`。
- Xcode 27 新建 Swift target 的默认设置:`SWIFT_APPROACHABLE_CONCURRENCY = YES`(即 `InferIsolatedConformances` + `NonisolatedNonsendingByDefault`)与 `SWIFT_UPCOMING_FEATURE_MEMBER_IMPORT_VISIBILITY = YES`。
- `UIView.animate(…completion:)` 在 SDK 里标了 `NS_SWIFT_DISABLE_ASYNC`,没有 async 版本。

### 1.3 外部环境

- `actions/checkout` 最新为 v7.0.1(2026-07-20)。v7 只在 `pull_request_target` / `workflow_run` 触发时改变行为,本仓库用的是 `push` / `pull_request`,可直接替换。
- GitHub 的 `macos-latest` 是 macOS 26 镜像,Xcode 最高 26.6(Swift 6.3.3)。Xcode 27 只在 `xcode-27` 预览标签上提供,官方说明可能排队,转正后标签也可能下线。
- CocoaPods 1.17.0 已发布;trunk 将于 2026-12-02 只读,此后无法再推送新版本。

## 2. 目标、非目标、反目标

### 2.1 目标

1. 示例 App 在 iOS 27 上能启动,UI 测试与 `iOSExampleTests` 全部通过。
2. 工具链升级:`swift-tools-version` 6.2,最低 iOS 18.0,Swift 6 语言模式之上开启 Xcode 27 推荐的前瞻特性。库、单元测试、示例工程、UI 测试**全部零告警**。
3. 用 iOS 18 起可用的新原语和更好的算法,提升第 5 节列出的几条热路径。
4. 发布 3.0.0,兑现源码里"下个大版本移除"的承诺。

### 2.2 非目标

- 不把 XCTest 迁移到 Swift Testing。XCTest 在 Xcode 27 下完整可用,迁移只是改写,不提升库的性能。
- 不改 `Promise` 基于 `OperationQueue` 的执行模型(线程池注入、按标识取消、2.1 的取消语义都建立在它上面)。
- 不把 `SwiftyLabel` 从 TextKit 1 换成 TextKit 2(排版结果可能变化)。
- 不改 `layer.contents` + TextKit 自绘的渲染策略。
- 除第 7 节列出的三项移除外,不改任何公开 API 的签名。
- 不升级本机 CocoaPods(1.16.2 下 lint 已通过)。
- CI 不切到 `xcode-27` 预览标签。

### 2.3 反目标

性能改动**不得改变任何可观察结果**:取色的四个颜色、缓存的淘汰顺序与内存计数、标签的排版尺寸与绘制像素,都必须与 2.1.0 逐位一致。每一条都要有对拍测试证明,而不是靠论证。

## 5. 性能改动

每一条都写明:改什么、为什么更快、怎么证明结果不变。

### P1. 并发原语换成 `Synchronization`

| 位置                                   | 现状                          | 改为                                   |
| -------------------------------------- | ----------------------------- | -------------------------------------- |
| `Promise` 的全部状态                   | 串行 `DispatchQueue` + `sync` | `Mutex<State>`                         |
| `RunFlag`(任务块是否跑过)              | `NSLock` + `Bool`             | `Atomic<Bool>`,release 写 / acquire 读 |
| `ResumeGuard`(continuation 只恢复一次) | `NSLock` + `Bool`             | `Atomic<Bool>` 的 compare-exchange     |
| `ImageCachePool`                       | `NSLock` + 5 个字段           | `Mutex<State>`                         |
| `SwiftyThreadPool`                     | `NSLock` + `OperationQueue?`  | `Mutex<State>`                         |

`Mutex` 内联存储 os_unfair_lock,无竞争时只有一次原子操作;`NSLock` 每次 lock/unlock 都是 Objective-C 消息发送;串行队列的 `sync` 还要走 libdispatch 的派发路径。两个标志位换成 `Atomic` 后完全无锁。

附带收益:这五处都能去掉 `@unchecked Sendable`,线程安全由编译器检查。内存告警观察者的 token 放进各自的 `Mutex` 状态里,`deinit` 在锁内移除,不需要 `nonisolated(unsafe)`。

临界区的划分与 2.1 **一一对应**(2.1 的取消语义、`registerValueWaiter` 的单一临界区论证都依赖它),只换锁的实现,不合并、不拆分任何临界区。

### P2. 取色 `getColors()`

现状的两处主要开销:

1. 用 `[UInt32: Int]` 字典给 250×H 个像素计数,每个像素一次 SipHash。
2. **给图里出现过的每一种颜色都新建 `UIColor`**,再做一次 `getHue`、可能再建一个提饱和的 `UIColor`、再取一次 `cgColor.components`(每次分配数组)。照片常有上万种颜色,而最后的挑选循环通常看前几十个就结束了。

改为:

- 计数:像素键收进一个数组,做两趟 12 位的 LSD 基数排序,再按段计数。O(n),无哈希。
- 候选:把 (次数, 键) 打包成一个 `UInt64`,建大顶堆,**按原排序规则(次数降序、键升序)逐个弹出**,弹出时才建 `UIColor`、做提饱和与 `isDark` 过滤,挑满 primary / secondary / detail 就停。
- 边缘色同理,只是规模小,直接排序。
- 下采样、像素缓冲区、所有 `UIColor` 判定函数都不动。

等价性:原实现先给全部颜色做过滤再排序;过滤与顺序无关,所以"按序逐个弹出再过滤"得到的序列与原来完全相同;挑选循环本身一行不改。

证明:测试 target 里保留一份 2.1.0 的 `getColors()` 原样拷贝作为参照实现,对一批生成的图片(随机噪点、渐变、双色、透明、黑白边缘、极端宽高比、灰度等)逐张比对四个颜色,要求 `UIColor` 完全相等。为此 `getColors()` 由 `private` 放宽为 `internal`。

### P3. `SwiftyLabel` 不再每次重建文本存储

现状:每次 `draw`、每次 `sizeThatFits`(`intrinsicContentSize` 也走这里,Auto Layout 一轮布局会问好几次)都会拷贝一份 `attributedText`、枚举四种属性补默认值、新建 `NSTextStorage`、重新挂上 layout manager,于是字形每次都从头生成。

改为:常驻一份 `NSTextStorage`,在 `init` 里挂好。影响合并结果的属性(`attributedText`、`font`、`textColor`、`paragraphStyle`、`shadow`)变化时只打一个"过期"标记,下次绘制或测量前才重建一次。容器上的属性(`numberOfLines`、`padding`、`lineBreakMode`)变化时让 layout manager 失效该容器的布局。

证明:新增对拍测试,对同一个 label 连续改各种属性,每一步都与"用同样属性新建的 label"比较 `sizeThatFits` 与绘制像素,要求完全一致——专门抓"缓存过期没失效"的那一类错误。

### P4. `ImageCachePool` 的 LRU 改为 O(1)

现状:每次超出容量都把全部条目按访问序号排序(O(n log n),还要分配一个数组),而且是在锁内。缓存满载时每次 `add` 都会触发一次。

改为:字典 + 侵入式双向链表(节点存在一个连续数组里,前后指针是下标,空位复用)。命中时把节点移到链表尾,淘汰时从链表头开始删。淘汰规则逐字保留,包括"至少删一个"和"新加入的条目在必要时也会被删"这两个边界行为。

证明:新增随机对拍测试,用 2.1.0 的排序淘汰算法写一个参照模型,对随机的增、删、查、改容量序列逐步比对"哪些条目还在"与 `memoryUsage`。

### P5. Toast 的 2.5 秒"假动画"

现状:淡入之后用一段 `alpha 1 → 1.0001` 的 2.5 秒动画当计时器。画面上没有任何变化,Core Animation 却在整段停留期间逐帧合成;XCUITest 也因此认为 App 一直不空闲(UI 测试的注释里记录过这一点)。

改为:淡入完成后 `Task.sleep(for: .seconds(2.5))`,再淡出。停留期间渲染循环空闲。淡入淡出仍用 `UIView.animate`(SDK 禁用了它的 async 版本)。

### P6. 零散的热点与过时写法

- `SwiftyGlobal.keyWindow`:不再先 `compactMap` 出一个中间数组。
- `SwiftyGlobal.modelName`:用 `withUnsafeBytes` 直接解码,不再用 `Mirror` 反射 256 个元素的元组。
- `SwiftyThreadPool` 的并发上限改用 `ProcessInfo.activeProcessorCount`(与 `hw.activecpu` 同值)。
- `UIColor.hex(String)`:直接在 UTF-8 字节上解析,不再分配中间字符串、逐字符插入。校验规则逐条保留。
- `SwiftyAlertView` 的随机 tag:`arc4random()` 改为 `Int.random(in:)`。
- `Promise.value()` 与 `UIImage.colors()`:显式 `nonisolated(nonsending)`(见第 3 节)。

## 10. 风险

| 风险                                                             | 缓解                                                                                               |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `Mutex` 的 `sending` 规则与现有闭包写法冲突,临界区被迫改形       | 已用探针验证 `PromiseTask`(含 `Operation`)、观察者 token 两种形态都能通过;改形时保持临界区边界不变 |
| `NonisolatedNonsendingByDefault` 改变测试里 async 方法的执行位置 | 全量测试验证;出问题时只对测试 target 关闭该特性                                                    |
| 取色或 LRU 的新实现在边界情形与旧实现不一致                      | 对拍测试覆盖随机输入与已知边界                                                                     |
| 本机只有 Xcode 27.1,tools 6.2 / Xcode 26 的兼容性无法在本地验证  | CI 的 `macos-latest`(Xcode 26.6)会验证;推送后看第一次 CI 结果                                      |
| `CODE_SIGN_IDENTITY` 等签名设置改动影响真机构建                  | 只改为 Xcode 自己推荐的值;模拟器构建不受影响                                                       |
