# SwiftyUI 2.1 设计：Promise 取消语义

**目标**：让 `Promise` 观察 `Operation` 的取消，使被取消的链条产生一个可被调用方看见的错误，而不是静默给出错误结果或永久挂死。

**范围**：GitHub issue [#3](https://github.com/haoking/SwiftyUI/issues/3)、[#4](https://github.com/haoking/SwiftyUI/issues/4)、[#5](https://github.com/haoking/SwiftyUI/issues/5)。

**基线**：`d7703e2`（2.0.0）。

---

## 1. 问题：一个根因，三种坏表现

`Sources/SwiftyPromise.swift` 全文没有出现过 `isCancelled`。链条因此完全不知道支撑它的 `Operation` 已被取消。

已实测确认的 Foundation 行为（探针见 §6.1）：**operation 在开始执行前被取消时，执行块不运行，但 `completionBlock` 仍然运行，且在其中可以读到 `isCancelled == true`。**

`fire()` 正是把推进逻辑挂在 `completionBlock` 上的（`SwiftyPromise.swift:399`）：

```swift
task.op.completionBlock = { self.fire() }
```

于是取消产生三种不同的坏表现：

| 被取消的对象                       | 现在的表现                                                                                                  | 严重度       |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------ |
| 链条中的任务                       | 执行块不跑，`completionBlock` 照跑 → `fire()` 推进 → **跳过该步，用陈旧值继续执行后续步骤**，最终"成功"终结 | 静默错误结果 |
| `always` 任务                      | 静默不执行                                                                                                  | 静默丢失     |
| `value()` 的 continuation 恢复逻辑 | **`try await promise.value()` 永久挂死**                                                                    | 挂死         |

第三条在 issue #3 中没有记录，是本次设计期间发现的。`value()` 把恢复 continuation 的 `BlockOperation` 作为一个 `always` 任务追加（`SwiftyPromise.swift:284`），而 `fire()` 的 `.finish` 分支投递 always 任务时**不挂 `completionBlock`**（`:401-405`）：

```swift
case .finish(let pending):
  for task in pending {
    task.start()          // 没有 completionBlock
  }
```

该 operation 一旦被取消，执行块不运行，`ResumeGuard` 永不 `claim()`，等待方永远不会被恢复。

### 1.1 真实可达路径

`SwiftyThreadPool` 监听 `UIApplication.didReceiveMemoryWarningNotification` 并调用 `removeAll()`（`Sources/SwiftyThreadPool.swift:57-63`），后者取消队列中的每一个 operation（`:113-124`）。因此在真机内存吃紧时，任何在飞的 promise 链都会命中上表。

`UIImage.colors(_:)` 建立在 promise 链上，所以这条路径直达公开 API。

---

## 2. 设计原则

**唯一的推进入口必须感知取消。** 修复不是在多处补检查，而是让 `completionBlock` —— 本来就是链条唯一的推进点 —— 承担取消判定。`always` 任务补上同样的 `completionBlock`，三种表现因此收敛到一个机制上。

---

## 3. 新增公开 API

```swift
public enum PromiseError: Error, Sendable, Equatable {
  /// 支撑该任务的 Operation 在开始执行前被取消。
  case cancelled
}
```

```swift
extension UIImage {
  /// 在后台分析图片主色。链条被取消时抛出 `PromiseError.cancelled`。
  public func colors() async throws -> (
    background: UIColor, primary: UIColor, secondary: UIColor, detail: UIColor
  )
}
```

两者都是纯新增。现有 `colors(_:)` 的签名与行为不变。

`colors()` 的返回类型是具名元组而非新结构体：与现有 `colors(_:)` 回调的四个具名参数保持一致，不引入调用方需要额外学习的类型。

## 4. 取消检测

### 4.1 判定：只有"没跑成"才算取消

`BlockOperation` 的执行块不检查 `isCancelled`。因此若取消发生在执行**期间**，工作其实已经完成 —— 此时把链条判为取消会丢弃一个有效结果。

判定条件是 `isCancelled && !didRun`，而不是单看 `isCancelled`。

`didRun` 标记跨线程（执行块与 `completionBlock` 可能在不同线程），用与本文件已有的 `ResumeGuard` 同形的加锁小盒子承载，不引入新的并发模式：

```swift
/// 记录一个 operation 的执行块是否真的运行过。
///
/// @unchecked Sendable 的理由与 ResumeGuard 一致：唯一的可变状态只经由
/// lock 保护的临界区读写，编译器无法验证，故为 unchecked。
private final class RunFlag: @unchecked Sendable {
  private let lock = NSLock()
  private var value = false

  func markRun() {
    lock.lock(); defer { lock.unlock() }
    value = true
  }

  var didRun: Bool {
    lock.lock(); defer { lock.unlock() }
    return value
  }
}
```

Foundation 保证 `completionBlock` 在 operation 结束之后运行，因此读到的 `didRun` 一定反映了执行块是否跑过。

### 4.2 `PromiseTask` 的字段变更

`private struct PromiseTask` 增加两个字段：

- `let runFlag: RunFlag` —— 由 `create(...)` 构造，与该任务的 operation 一一对应。
- `let onCancelled: (@Sendable () -> Void)?` —— 默认 `nil`，仅 `value()` 传入（见 §4.4）。

### 4.3 链条任务

`operationBuild` / `operationBuildT` 构造的 operation 在块首调用 `runFlag.markRun()`。`fire()` 的 `.run` 分支据此判定：

```swift
case .run(let task):
  // 只捕获 flag，不要捕获 task —— task 持有 op，把它捕进 op 自己的
  // completionBlock 会造成 op → completionBlock → task → op 的环，
  // 正是下面 [weak op] 想避免的东西。RunFlag 不引用 op，捕获它是安全的。
  let flag = task.runFlag
  task.op.completionBlock = { [weak op = task.op] in
    if op?.isCancelled == true && !flag.didRun {
      self.markError(PromiseError.cancelled)
    }
    self.fire()
  }
  task.start()
```

`markError` 先于 `fire()`：`markError` 置 `isError = true`，随后的 `fire()` 会走到 `isError` 分支，丢弃剩余任务并进入终结。这复用现有的错误终结路径，不新增状态。

`[weak op]` 是为了不让 operation 通过自己的 `completionBlock` 持有自己。

### 4.4 always 任务

`.finish` 分支改为同样挂 `completionBlock`（同样只捕获 `flag` 与 `onCancelled`，不捕获 `task`）：

```swift
case .finish(let pending):
  for task in pending {
    let flag = task.runFlag
    let onCancelled = task.onCancelled
    task.op.completionBlock = { [weak op = task.op] in
      if op?.isCancelled == true && !flag.didRun {
        onCancelled?()
      }
    }
    task.start()
  }
```

`onCancelled` 只有 `value()` 传入：它在此处以 `PromiseError.cancelled` 恢复 continuation。具体地，`value()` 现在这样构造它的 always 任务：

```swift
guard appendAlwaysIfUnfinished(
  .create(nil, .background, alwaysOperation, onCancelled: {
    guard resumed.claim() else { return }
    continuation.resume(throwing: PromiseError.cancelled)
  })
) else { ... }
```

`ResumeGuard` 保证只恢复一次，因此"块正常跑完（返回当前值）"与"块被取消（抛 `.cancelled`）"两条路径天然互斥安全，无论哪条先到。

用户经 `always(_:)` 追加的任务不设 `onCancelled`：链条此时已经终结，错误无处可去。这一点写进 `always(_:)` 的文档注释。

## 5. issue #4：终结后追加

`then` / `always` 改为在同一个临界区内完成"未终结才追加"的判断，与已有的 `appendAlwaysIfUnfinished`（`SwiftyPromise.swift:344-350`）同形：

```swift
@discardableResult
public func then(...) -> Promise {
  let accepted = withState {
    guard !isFinished else { return false }
    tasks.append(.create(...))
    return true
  }
  if !accepted {
    assertionFailure("向已终结的 Promise 追加 then；该任务永远不会执行")
  }
  return self
}
```

debug 构建当场暴露，release 构建保持无操作（与 2.0 行为一致）。返回值仍是 `self`，链式写法不受影响。

`always(_:)` 同样处理。

**为什么不是"立即执行"**：那会让 `isFinished` 不再是终态，与它作为全局门闩的现有设计矛盾；且立即执行的 `then` 若抛错，链条已终结、`fire()` 不会再推进，错误无人接收 —— 又制造一处静默丢弃。

## 6. 测试

**每条修复都必须有一个还原修复后会变红的测试。** 这是 2.0 反复出问题的地方（七次"测试通过但什么都没保护"）。

### 6.1 取消的确定性构造

不依赖时序：用 `isSuspended = true` 的队列让 operation 排队但不开始，`cancel()` 之后再放行。本设计的 Foundation 行为结论即由此法实测得出：

```swift
let q = OperationQueue()
q.isSuspended = true
let op = BlockOperation { blockRan = true }
op.completionBlock = { [weak op] in
  completionRan = true
  cancelledAtCompletion = op?.isCancelled
}
q.addOperation(op)
op.cancel()
q.isSuspended = false
// 结果：blockRan == false，completionRan == true，isCancelled == true
```

### 6.2 必须覆盖

| 场景                           | 断言                                                                                          |
| ------------------------------ | --------------------------------------------------------------------------------------------- |
| 链条中的任务在开始前被取消     | `catch(_:)` 收到 `PromiseError.cancelled`；后续任务**不**执行                                 |
| 同上                           | 链条不以陈旧值"成功"终结                                                                      |
| `value()` 在链条被取消时       | **抛出** `PromiseError.cancelled`，而不是挂死 —— 必须带超时，否则回归时的表现又是挂死而非失败 |
| `value()` 的 always 任务被取消 | 同上；这是 §1 第三行那条挂死路径的直接回归测试                                                |
| 取消发生在执行**期间**         | 结果**不**被丢弃，链条正常完成（§4.1 的判定）                                                 |
| 终结后 `then` / `always`       | release 语义下任务被拒且不执行                                                                |
| `colors()` async 变体          | 正常路径返回四色；取消路径抛 `PromiseError.cancelled`                                         |

超时机制沿用 2.0 引入的 `withTestTimeout`（`Tests/SwiftyUITests/` 内），不新造。

## 7. issue #5：测试脚本的模拟器选取

`Scripts/test.sh:13` 与 `Scripts/uitest.sh:21` 目前取 `tail -1`，选中哪台取决于本机装了什么以及 `simctl` 的列出顺序。取色测试对屏幕 scale 敏感，换机器或换 runner 世代会产生无法复现的失败。

改为：优先匹配一个指定机型，缺失时回落到现有的 `tail -1`，并**打印最终选中的设备名与 UDID**。

动态查找本身必须保留 —— 硬编码 `name=iPhone 16 Pro` 在本仓库直接失败，因为 arm64 与 x86_64 变体都匹配，xcodebuild 拒绝有歧义的 destination。要改的只是"在可用设备之间的挑选是任意的"这一点。

日志里能看见目标是什么，是这条改动的一半价值。

## 8. 兼容性

2.1 是次版本号。三项改动中两项改变可观察行为：

- **取消现在产生错误。** 先前的行为是"静默给出错误结果"或"挂死"，不存在可被合理依赖的契约。
- **debug 断言**可能让原本就有潜伏 bug 的调用方在 debug 构建下断言失败；release 构建不受影响。

`colors(_:)` 的回调在链条出错或被取消时不会被调用 —— 这一点在 2.0 就已成立（它以无参 `.catch()` 收尾，错误被吞），2.1 补进文档与 CHANGELOG，并提供 `colors()` async 变体作为可处理错误的替代。
